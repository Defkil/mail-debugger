# Release review: mail-debugger 0.4.0

Review completed on 2026-10-11. It started at `32139eb760e70964cf51d7d89eeef221ae447b4f`, on `feat/claude-d8f0/mail-debugger`, against `main` baseline `581c0f5`, with a clean working tree. The review covers the complete branch, including the completion plan and its implementation notes.

Severity: **high** means data loss, a security boundary failure, or a release blocker; **medium** means incorrect public behavior or a meaningful reliability gap; **low** means polish or a limited robustness problem.

## 1. Canonical mailbox, REST, SMTP, and lifecycle

REST Host/Origin/token checks execute before routing, and the new encoded-path regression proves encoded spellings cannot reach protected handlers unauthenticated. Download responses preserve source/attachment bytes, cap and escape filenames, force executable MIME types to octet-stream, and carry attachment disposition, sandbox, no-store, and nosniff headers. Static path checks reject Windows backslashes, NULs, malformed encoding, and root escape; the packaged web assets are trusted local files.

High finding, `apps/server/src/config.ts:300`, `libs/client/src/lib/api-client.ts:161`, and `apps/server/src/mcp/bridge.ts:131`: the no-whitespace token check accepted controls/non-ASCII values that Headers rejected while echoing the secret in an error. Fixed in `57c676b` and `bec4d55`: reject unsupported tokens with a static nonsecret message before constructing headers, and mask custom-header construction errors. Regressions cover API/MCP configuration, client/bridge diagnostics, and malformed custom authorization headers.

All adapters use the same transactional `MailService`, monotonic IDs, filters, and post-commit events. SMTP bounds DATA and drains excess input without retaining further chunks, rechecks capacity when committing, and maps storage/message limits to 452/552. Concurrent delivery, migration rollback/backups, cursor identity, abort/disconnect cleanup, and graceful shutdown are covered. Snapshot persistence is explicitly asynchronous: a crash can lose changes since the last completed snapshot, and the byte limit measures stored content rather than process RSS. These are documented development-server limits, not durability or production-service claims.

## 2. IMAP

| Severity | Location                                     | Finding and resolution                                                                                                                                                                                                                                                                                                                                                                                     |
| -------- | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| High     | `apps/server/src/imap/pending-work.ts:16`    | ImapKit bounded individual lines/literals but allowed unbounded pipelined commands behind asynchronous FETCH/CHECK and mailbox notifications retaining deleted sources. Fixed in `3405234`: 64 commands/4 MiB input, 1024 notifications, and a separate retained-source budget; exceeding a limit disconnects the session. Tests stall CHECK and exercise command counts/bytes and notification retention. |
| Medium   | `apps/server/src/imap/imap-server.ts:93`     | Incomplete implicit-TLS handshakes had no ImapKit session, so shutdown did not close them within its grace period. Fixed in `3405234`: track all accepted raw sockets, cap raw connections, and destroy remaining sockets on shutdown. The regression leaves a handshake unfinished and checks shutdown.                                                                                                   |
| Medium   | `apps/server/src/imap/imap-server.ts:143`    | STARTTLS inactivity could send a plaintext BYE into a TLS handshake. Fixed in `3405234`: destroy the negotiating socket instead.                                                                                                                                                                                                                                                                           |
| High     | `apps/server/src/imap/output-control.ts:364` | The 1 MiB ENVELOPE/BODYSTRUCTURE estimate cap underestimated arbitrarily large headers/structures before output allocation. Fixed in `3405234`: conservatively charge escaped header/source size. A repeated large-envelope FETCH is refused before output is built.                                                                                                                                       |
| Low      | `apps/server/src/imap/output-control.ts:83`  | A pending drain timer/listener outlived a disconnected socket. The restricted INBOX profile is coherent: credentials and TLS gating apply to LOGIN and AUTHENTICATE; capabilities change after STARTTLS; EXAMINE is read-only; FETCH Seen, STORE, subscription, and expunge mutate the canonical mailbox before successful output. Tests exercise UID/sequence distinctions, concurrent REST/SMTP/IMAP changes, IDLE, persistence/migration, protocol errors, literals, flags, unsupported operations, and slow readers with ImapFlow and raw transcripts. Targeted review verification passed 32 IMAP tests, lint, and server typecheck.

Medium finding, `apps/server/src/mail/mail-service.ts:453`: accepting UID 4,294,967,295 made the following UIDNEXT overflow the 32-bit protocol range. Fixed in `3137024`: reserve that final value for UIDNEXT and refuse further delivery without changing state. The boundary test accepts the preceding UID, checks the exhausted counter, and proves refusal and clear never reset it. The precise limit is documented.

Acceptable disclosed limitation: random UIDVALIDITY removes deterministic rapid-restart reuse, but cannot guarantee collision-free or monotonically increasing values across discarded/recreated datasets. [RFC 3501 section 2.3.1.1](https://www.rfc-editor.org/rfc/rfc3501.html#section-2.3.1.1) requires stronger continuity when prior-session UIDs do not persist. This development profile recommends `--data-dir` for persistent cache continuity and makes no complete RFC or desktop-client interoperability claim. Within a retained dataset, UIDVALIDITY/UIDNEXT/flags persist and UIDs are never reused, including after clear; exhaustion refuses new mail.

MCP schemas are strict and cap tool filters, pages, body bytes, attachment chunks, and waits. The mutation gate controls both tool listing and dispatch; clear requires count confirmation and checks it transactionally. Server tools expose data rather than interpreting email instructions, and errors are bounded without internal details. The HTTP token is independent of the REST token, with Host/Origin guards before the SDK and a stateless transport profile. Wait slots release on success/error/cancellation/shutdown and share the canonical service's global cap.

The bridge uses stderr for diagnostics, stdout for protocol, forwards schemas/cancellation, and never starts a mailbox. The 2025 stateless fallback cannot propagate all HTTP cancellation; server-side waits end within the documented 30-second MCP limit. Targeted review evidence: client 109 tests with coverage, CLI 144 tests with coverage, MCP/bridge unit tests and 7 real-process stdio tests, plus lint/typecheck across all owned projects. Terminal mail fields are sanitized in both formatted and interactive paths; JSON escaping preserves raw data without executing controls. The pinned pino-pretty implementation also strips unsafe controls from messages/keys/error stacks, while production logs serialize JSON.
